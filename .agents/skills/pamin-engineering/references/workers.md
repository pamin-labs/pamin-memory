# Cloudflare Workers

How a Cloudflare Worker in TypeScript meets `core.md`; read it first. The directory's `AGENTS.md` says what its Workers route and names their modules.

- **No business logic.** A Worker routes calls, forwards what the platform or a gateway already decided (a signed identity, place headers from Cloudflare's own lookup), and starts, wakes and fails over containers; anything about users, tenants, keys, limits, entitlements or content belongs to the server, the gateway or a module.
- **Pure functions apart from the runtime.** Path rules, header handling, failover, instance choice, catalogue parsing and settings checks live in their own modules, each tested with Vitest without the Workers runtime; the entry file only wires them to the Worker and its Durable Objects.
- **No decisions in the entry file.** Every decision (which port, which headers pass, whether a body can be buffered, when to retry a start, how long to wait for health) is a tested function in those modules, and settings read from `env` are parsed by one there. Timeouts and limits are named constants there, never inline. The entry file keeps only checks of the runtime's own state, such as whether a container is already running.
- **No non-null assertions.** A container is read through the Durable Object's guarded getter, which throws a clear error when the class has none.
- **Every module is named by its path** in the directory's `AGENTS.md`, with its purpose. A test fails on a TypeScript file (tests aside) in a folder that file does not name and on a named file that is gone, so a new module is described there first.
- **A request without `Content-Length`** is handled explicitly, streamed or read up to a limit, never refused by default.
- **Ports and path prefixes are written once,** in one module, and a test or the catalogue generator checks them against the services, their `.env.example` and any client that names them.
- **No user-facing text.** A Worker answers with status codes, headers and declared problem bodies only; anything a user reads comes from the app's messages or the server, in the user's locale.
- **Security headers** are set by one function on every answer a Worker makes; assets the platform serves without the Worker get the same headers from its headers file, and a test checks the two agree.
- **Config.** The Wrangler config is the source of names, domains and environments, never code or scripts. The account a deploy acts on is a deploy setting in the secret manager, which the `ops` command sets on Wrangler's own process alone, so no config, login or loaded shell picks it. Environments do not inherit containers, Durable Objects, bindings, routes or secrets, so each lists its own, and a test checks the names agree. Generated binding types are regenerated with `wrangler types` after a config change, never edited.
- **One deploy path.** Deploys and local settings go only through the repository's `ops` command, which reads the environment's settings from the deployment's secret manager once, checks them, and sends secrets through stdin so they are written nowhere. Nobody runs a Wrangler command that changes a Worker by hand (`deploy`, `versions upload`, a `secret` write, `triggers deploy`, `delete`); a repository hook refuses them to agents, while read-only commands and `--dry-run` pass. A rollback is the engineer's, by hand, and the next `ops` deploy brings the Worker back in step.
- **Typed end to end.** No `any`, and no `as` cast except on generated types. Values from settings, another service or a request are checked with a guard that has a test with malformed input, and a `switch` over a closed set ends with `default: x satisfies never`.
- **Dependencies** are pinned exactly, and a check fails on an unused one. Biome warnings fail the check, and `biome migrate` runs after a Biome upgrade.
