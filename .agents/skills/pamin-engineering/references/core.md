# Core engineering rules

Read this before writing or changing any code, in any language, and again before a PR opens. Every repository that imports this file holds its code to these rules. The bar: high performance, low resource use, fast builds, and clean, DRY, decoupled code that is easy to maintain and extend. Each repository's `AGENTS.md` names its layers, how it meets these rules and the tests that check them; a language's reference adds only that language's mechanisms. Its source is the public `pamin-labs/skills` repository; repositories install it with the skills CLI and change it only there.

## Before writing anything

- **Does it need to exist?** Build what a real caller needs now. No speculative options, layers, traits, interfaces or config; add them when a second real use appears.
- **One implementation per concern.** Search the repository and its shared libraries for the concern first, and extend the module that owns it through its interface; never add a parallel version with its own rules.
- **Do not reinvent what exists.** Reach, in order, for the repository's own implementation, the service's official SDK, the standard library, the platform, a dependency already in the tree, then a maintained, widely used one; write your own only when none meets the need. The PR's "Reused" section says what was searched, reused and hand-written, and why; hand-written code one of those covers is a defect review sends back.
- **Dependency versions.** Lock files pin exact versions. A published library requires caret minimums so consumers can unify, pinning exactly only with a stated reason.
- **Before adding a dependency,** check its maintenance, licence, and added build time and bundle or binary size, and record them in the PR.

## Shape of the code

- **One rule, one place.** A change to a rule touches one function or module; if you must edit the same logic in two places, the logic is in the wrong place. Each rule, schema, header, path and setting name is defined once, in its owning module, and imported elsewhere; before adding a helper, search for one.
- **Business logic lives in one layer per area,** apart from transport, views, wiring and storage; each area's `AGENTS.md` says where.
- **A directory says what its code is.** New code goes into the directory its area's `AGENTS.md` names for its layer or concern, never beside them at the top, and that file names each of its parts by path. A new directory at that level updates that `AGENTS.md`, and any layout test's list, in the same PR; where no test reads the list yet, review checks it.
- **Small functions with one job,** names that say what they hold, comments that say why, not what, and no dead code. Small functions cost nothing where the compiler can inline them (static dispatch in one compilation unit, or with LTO); a call it cannot inline (a function pointer, an interface, a foreign-language boundary) made per element in a hot loop gets a bulk form that takes the batch, and inlining on a hot path is confirmed by measurement or the disassembly, not assumed.
- **Deep modules.** A module's interface is much simpler than what it hides. Review flags a module whose interface is as complex as its body, a parameter passed through layers that do not use it, and one design decision (a format, an order, a limit) known by two modules.
- **Names are consistent:** one word per concept across the codebase and symmetric pairs (`begin`/`end`, `source`/`target`), never two words for one thing or one word for two. Each variable lives in the smallest scope, and a value is checked where it is used.
- **One reason to change per file.** A file holds one business area's code and does one job for it; a file that does two (parsing and deciding, fetching and drawing, a rule and its transport) is split along them. Size follows from this: a file is split when it holds a second concern, never to meet a line count.
- **High cohesion, low coupling.** Code that changes together lives together, grouped by domain or feature inside its layer, never in grab bags by kind that span domains. Modules talk through small public surfaces: no reaching into another module's internals, and no chains through another object's fields (`a.b.c.d`).
- **Each domain keeps its own language.** A domain's types are named in its own vocabulary; a concept two domains see differently (a game's player, a chat's end user) is converted where one calls the other, never one shared type stretched to serve both.
- **A pure core, effects at the edge.** Rules are plain functions over values, with no I/O, clock or randomness of their own (time and seeds are passed in), so they are tested without stubs; I/O, logging and the clock stay in the code that calls them.
- **Readable control flow.** Decide in the caller and let leaves compute: branches move up, loops move down into functions that take a batch. Early returns over nesting; no boolean parameter that switches a function between two behaviours (write two functions); several related parameters become one typed value; a function answers a question or changes state, not both, unless one atomic step needs both, and then its name says so.
- **Comments claim only what the code guarantees.** A guarantee that waits on later work is named as not yet given.
- **Define errors out of existence** where the semantics allow: an empty range returns empty, closing a closed handle is done; the error set keeps what a caller can act on.
- **No recursion whose depth input controls:** an explicit stack with a named bound instead, since a deep input would overflow the stack, a crash no error catches.
- **Errors carry context** and are handled once, where something can be done: returned or logged, never both, never swallowed.
- **Types over strings and integers.** Ids, units, amounts and times are named or standard types, never bare strings or numbers; input is parsed into them at the boundary, so inner code only sees valid values. Where a unit cannot be a type (a local, a config name, a metric, a C field), the name carries it, units and qualifiers last (`timeout_ms`, `latency_ms_max`).
- **Illegal states are unrepresentable.** Fields that are valid only together or only in one state form a tagged union (an enum with payloads), never a struct of optionals plus a flag. Each fact is stored once; a derived value is computed, or, where a measurement says to store it, has one owner that updates it.
- **Trust boundaries are explicit.** Identity, tenant, end user and project come from authentication, never from a request body, a tool argument or a model.
- **Model external data with types.** External JSON (requests, MCP results, other services' answers, webhooks, files another program writes) is parsed into typed structs and enums that ignore unknown fields, and requests are serialized from typed structs; no hand-built JSON, untyped lookup chains or substring searches. A value stays opaque only when a protocol requires it echoed back unchanged, and the code says so.
- **No hard-coded value in more than one place.** Every port, address, URL, id, version, limit, price, page size, locale list, file name and default is defined once, where it is owned (a module's constant, a Makefile variable, a Dockerfile `ARG`, a Wrangler config, `.env.example`); everything else reads it or is checked against it by a test or a generator. A literal that names a value owned elsewhere is a bug, in code, config, scripts, tests and docs alike. A value two projects use has one source, and a test or a generated file keeps the other in step.
- **Text and locales have one source.** The locales are listed once per project, and a test keeps every project's list equal; adding a locale touches that list and the message files, nothing else. A locale is a full BCP 47 tag (`zh-Hans`, never `zh`), the same in every layer and in stored data, so no layer maps one spelling to another. Text in several languages is a map keyed by locale, never a field or branch per language (`nameZH`, `locale === "en"`). The fallback from a locale to its base language and then the default is written once per project, never in SQL or a view. Every string an end user reads is a message in their locale, including what the server sends (notices, refusals, safety text); dates, numbers, plurals and language names come from the platform's locale APIs. Prompts and model schemas are built from the locale list, never naming two languages. No code assumes a script, spaces between words or a text direction.
- **Deployments have no defaults.** A setting a deployed binary or service must be given has no fallback in code: a missing or empty one stops the program at start, naming itself. Only local use (a cache directory, a socket, a Makefile, Vite, a benchmark) names local values, each once.
- **Shared state has one owner,** a type or a task, keeping each lock next to the fields it guards.
- **Built files are never committed.** Build output, benchmark and evaluation results, model caches, indexes and generated caches are git-ignored; only generated files a gate checks (snapshots, generated queries, API documents) are committed.
- **Extensibility check before every PR.** One more of something the code already has (an operation, setting, route, module, model, locale, transport) touches its one definition plus its tests, messages and docs; if it needed more places, fold them into one source in the same PR.
- **Tests meet the same bar as code.** A test builds requests from typed values, decodes answers into the API's own types (never a store row), compares JSON by decoding it, never as strings, and names a value defined elsewhere from where it is defined.
- **No deferral inside a PR's own code.** A written rule broken by code the PR adds or touches is fixed in that PR, in its own commit; a follow-up is only work outside the PR's concern.

## Layers, domains and decoupling

- **Layers point one way:** entry, wiring, transport, domain, then store and integrations, then values. Dependencies point only rightward, and a test fails on one that points back; each language's reference says how that test reads imports. A new module or crate goes in its layer's directory, never beside the layers.
- **Transport only translates.** A handler, middleware or CLI command parses the request into types, calls one domain function and shapes its result as the API's types. Any business rule there (a refusal, quota, limit, metering decision or check of any kind) is a bug; a middleware may read the request but calls the function that decides, which declares the error.
- **Transport never reaches the store:** no call, type or error from it. A domain function that only passes a call through is still worth having, so a later rule has one place to go: this is the price of the layering, and holds only at a layer boundary. Inside one layer a function that only forwards is a shallow module, folded into its caller.
- **Each layer converts at its edge.** Row types never leave the store: store read types become domain types, then wire types, so a schema change fails to compile at a conversion instead of silently changing the API. A domain's public functions and fields use its own types; the only store type it shows is its store handle; a type several domains and the store share is a value.
- **A domain owns its data.** It calls another domain's service, never its queries or tables; the caller's domain, not the store, orchestrates cross-domain work. Each store function is called from one domain only, and a test fails otherwise.
- **A domain module holds its service, its types, its errors and its rules.** It depends only on the store, on integrations through traits or interfaces it declares, and on other domains' services; never on an HTTP framework, MCP transport code or the API layer.
- **Wiring is in one place.** The entry point or app module builds each service once and hands each transport the services it uses. A background task is domain code on a schedule, under the same rules, owned by the wiring that awaits it at shutdown.
- **Each handler group sees only its own services.** Each business area registers its operations in its own file and receives only its service and the caller's identity; an API is never one handler holding every dependency.
- **Traits and interfaces are declared by their consumer,** with only the methods it calls. Functions return concrete types.
- **A second copy of a loop over an SDK is a bug:** one helper per repeated SDK flow, in its integration module.
- **A rule is computed in one function,** which other domains call rather than restate. What a client must do first is that function's answer, not flags the client orders.
- **A counter and its refusal come from one function.** The "left" figure a caller is told comes from the function that refuses, and a test checks they agree.
- **A closed set of values is one named type with one list.** Wire enums and schemas are built from that list, never written again in a tag or string, and a test checks it against the database's check constraint. A store value is never a wire name.
- **Modules are named for what they hold;** no `utils`, `common`, `models` or `helpers`. Each covers one concern, with a small public surface, private by default. A file covers one business area, not one type, in this order: imports; types; constants and statics; constructors; methods grouped by type, public first; plain helpers, in rough call order. A type is declared before the code that uses it. An enum's constants follow its type at once.
- **Writes are safe to repeat.** A write a client or retry may send twice is idempotent: a repeat returns what the first stored and changes nothing more. A repeated delete, or a delete of an id already gone, answers as done (204). A call it makes to another service is outside the transaction and safe to retry, with that service's "not found" counting as done. Steps are ordered so a failure part way leaves no gap.
- **Caches, and state kept per end user, tenant or key beyond a request, are bounded:** a structure with eviction, never a map pruned by hand. Per-end-user work that must be serialised is serialised in the database (a lease or row lock), not in one instance's memory, so instances stay stateless.
- **Hot paths keep their database round trips flat.** A request's round trips do not grow with an end user's data: no per-request `count(*)`, `offset` or `max()` over a growing set. Keep counters, use keyset pagination with matching indexes, and batch independent reads. A list that grows is paged by an opaque cursor, and a screen that needs one item asks for it by id, never reads the list to find it.
- **Parse once.** Large values (manifests, schemas, prompts, models) are parsed once and cached by version in a bounded cache, never copied per request. Answers are streamed rather than buffered where they can be.

## Errors, data, settings and calls to other services

### Errors and API documents

- **Values are leaves.** A type two layers share is declared once, in a value module that imports no service. The store reads and writes these types and never imports a domain, a model harness or transport.
- **One code, one error.** Every error a client is told about is declared once, in the domain that owns it, with a kind (invalid, forbidden, conflict, too many, unavailable, ...) and a stable code; a code declared twice fails at start or in a test. A limit says when it lifts.
  - A business error belongs to the domain whose rule raises it; the store keeps only data errors (not found, busy), and the domain maps a store error that transport must act on to its own error.
  - Transport answers any declared error by its kind, with no table of every domain's errors, and never names the store's errors.
  - A layer with nothing more particular to say reuses the error of its kind and adds context, never declaring the same code again.
- **What a client decides from an error is the server's to say.** An error carries whether it is retryable, from its kind; a client reads that, never its own list of codes.
- **An API document lists the codes its operations send, and no other.** Each operation, and each middleware where installed, declares its errors, and the document's code enum is built from them, so a client never maps a code it cannot receive. A document builds without warnings. A file committed from a generator (an API document, a catalogue, a list another project reads) is checked current by a test or CI step.
- **Money is one named schema.** An API document declares its money unit once, as a named schema every money field uses, and clients recognise a money field by that schema, never by a name suffix.
- **Personal text never goes in a URL,** because URLs land in logs, history and caches: a search over personal data is a POST, and its audit records the actor and what was found, never the text.
- **APIs are isolated.** Public, operator and internal APIs each have their own module, port or listener, and document; none imports another's modules, and the operator API is reachable only from its own host.

### Data and transactions

Read `data.md` before touching a query, a migration, a transaction or a list: it holds the storage rules (transactions, the pooler, SQL files, checked literals, query plans, migrations).

- **A write that charges, and that a client may send twice, takes a client id,** generated by the client, the same on every attempt and unique per caller. A repeat with the same id and request returns what was stored and charges nothing; the same id with a different request is refused.

### Settings and switches

- **Settings have one source each.** A deployment setting is read in one place at start into a typed config. `.env.example`, or the service's own list of required names, names it once, with a comment and no value, and a test keeps the two in step. It has no default in code. Deployed values live only in the secret manager, and the deploy reads them from there, so none sits in a file or only in the platform. A setting only the deploy reads starts with `DEPLOY_`, so the service's check skips it by one rule. Nobody loads `.env` into a shell (no `source`, direnv, or the secret manager's CLI wrapped around a shell): the tools read it themselves, and a loaded shell's values would win over it and reach every other tool.
- **Product settings live in the database.** Models, prices, plans, limits, retention and the like are named with their defaults in one settings module, stored only where they differ, changed through the operator API with an audited reason, and read live, never copied at start.
- **No development-only behaviour in production code.** Local runs use a stub of each service ("Stubs exist only for tests and local runs"), never a back door.
- **A kill switch is a product setting, judged in one domain function** that every entry point of its kind already calls, never in a handler. Operators are warned while it is on, and its refusal is a declared, non-retryable error.
- **Operator writes are audited and safe to repeat.** Every operator change carries a reason, written in one transaction with its audit record.

### Calls to other services and models

- **Every call a request waits on has its own deadline and fallback.** The deadline is named once beside the call (a constant, or a setting when operators tune it) and set on the call's context or future, never left to an HTTP client's default timeouts. When it passes, it is logged and the request goes on without the result or fails with a declared error.
- **One integration module per external service.** It wraps the official SDK, or a small typed client where there is none, and holds the service's URLs and ids as constants. A domain declares the trait or interface it calls and the wiring hands it the implementation; only the integration module imports the SDK.
- **Model and inference calls have one owner.** Every model call goes through one layer (a harness, inference module or pool) that names each call's task, budget and settings in one list and prices or meters its usage. A new model call gets a row in the project's list of model calls, with measured cost and latency, and a roadmap entry.
- **A change to model behaviour passes the evals over repeated runs,** since one run of a model proves little; failing and flaky cases are recorded in the PR and the roadmap.
- **Cost is metered and watched.** Every metered unit is recorded once, by the layer that owns billing: for a module a hosting platform serves, that is the platform, never the module's own code. Spend no single end user causes (background work, batch jobs, re-checks) is metered too, attributed to no end user, and a total past an operator-set threshold raises an alert.
- **Stubs exist only for tests and local runs:** reachable only from tests, the benchmark and the local runner, and a test fails when production code imports one.
- **Logs carry ids, counts and durations only,** never message text, end-user content, tokens, secrets, request bodies or other personal data. Each request or call writes one line, joined to its trace.

## Resources, build speed and measurement

- **Resources.** Idle processes hold little memory, and work that can wait runs in the background with a budget. A background loop rests when idle, backing off to a cap named once, and the instance that adds work wakes it, so an idle service costs almost nothing.
- **Build speed.** Shallow dependency trees, one well-chosen dependency over several small ones, unused default features off. Split code so an edit rebuilds little, with heavy dependencies (inference, TLS) behind the modules or features that need them.
- **Footprint.** Release builds are as small as the language allows without losing safety checks the product relies on.
- **Measure before and after** any change claimed faster, smaller or cheaper, on the entry point the product calls, with both numbers and the method in the PR, as `performance.md`'s measurement table says. A claim without a measurement is removed.

## Working and review

- Everything committed is English: code, comments, logs, commits, PR titles and bodies, documents.
- Never write tokens, keys or credentials to files, commits or logs.
- **Nothing lives only in a conversation.** Work found and not done (review follow-ups, audit findings, a flaky test) goes into the project's roadmap in the same session; the user's decision goes into a decision record before or with the change.
- **Rule scans** of a whole repository follow `rule-scan.md`.
- **Rule documents stay lean.** An `AGENTS.md` keeps rules, mechanisms, names and test names; history, worked examples, long lists and measured figures go to `docs/` pages beside it, each linked from it with a line saying when to read it. A rule that appears in both changes in both in one PR.
- **Before a PR opens,** rebase on the latest `main`; if `main` gained something overlapping, build on what landed and say what was reused and removed. Run the gates of every `AGENTS.md` the change touches, locally. In the team's own repositories gates run on the engineer's machine to keep CI cheap: CI runs a project's full gates once, for a PR into `main`; a PR stacked on another branch runs none, and the stack's PR into `main` runs them on the whole. Other repositories run CI on every pull request, as open-source projects do.
- **Review before every PR.** Check the whole diff, tests included, against every rule of each `AGENTS.md` it touches and the references they import, fixing misses in new commits; then have it reviewed by a second reader (in the team's repositories, the coordination tool's peer-review skill; elsewhere, your own review step) and put its verdict and findings under the PR's verification. The agent opening the PR reviews delegated work the same way, itself, never on the delegate's report alone.
- **A PR merges only when its final commit is proven:** GitHub reports it clean, every check has passed (a failed or pending check blocks it, however small the change), its tests pass, and, for a deployed or shipped service or binary, an end-to-end check (a local acceptance run or staging) has passed on that same final commit, never a run from before the last review fix. Since CI runs once per PR, whoever merges re-triggers the gates on the final commit and merges only once they pass.

## Commits and PRs

These hold in every repository that uses this skill, except the first, which only the team's own product repositories follow.

- **Intents, in the team's own product repositories only** (those set up with the coordination tool, whose commit skill, hooks and CI hold the details): before editing, declare an intent and work on its branch `<type>/i-<number>-<slug>` (no person or tool names); the PR description says `Intent: I-<number>`, and CI rejects a PR without a live intent for its branch. Check the briefing's intents of products this one uses before changing code that depends on them. They keep this flow even when their code is public or published as a library. Any other repository, whether a community project made for outside use and contributors or someone else's project, skips intents, intent-numbered branches and the coordination file and takes the usual open-source flow (Conventional Commits, PR review, CI on every pull request); a community project the team publishes names none of the team's internal tools in its documents.
- Conventional Commits with a required scope (`fix(engine): ...`) for commits and PR titles; first line and title at most 72 characters, scope included. Count before committing: a pushed commit is not rewritten without the user.
- One logical change per commit, each building and passing alone; refactors, behaviour changes and formatting are separate commits.
- A PR covers one concern, reviewable in one sitting; large work is a stack of PRs, each mergeable alone, and a stacked PR names the PR it builds on. Its description has a summary, the changes, what it reused, how it was verified (with numbers for performance, and for an interface change the screenshots of `web-interface.md`), and any risk or follow-up.
- No agent attribution: no `Co-Authored-By` trailers, session URLs or ids, or "Generated with" footers. Some tools append one when they create or edit a PR, so read the description back after each such call and remove it.
- The commit author is the engineer's own git identity, never invented; if missing, stop and ask, then save it as `GIT_AUTHOR_NAME` and `GIT_AUTHOR_EMAIL` in the environment settings.
- Never squash-merge; keep every commit.
