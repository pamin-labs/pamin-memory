# Performance

Read this when touching a request's hot path (named in the service's `AGENTS.md`), a pool, start-up or a benchmark, or before claiming a change is faster, smaller or cheaper, in any language. Read `core.md` first: its "Parse once", "Hot paths keep their database round trips flat", bounded caches and state and "Measure before and after" rules apply too and are not repeated here, nor is `data.md`'s "Calls to other services stay out of transactions". `rust.md`, `go.md` and `zig.md` say how their code meets these.

- **Estimate before designing a hot path.** Count its operations (round trips, disk reads, bytes moved, cache misses), multiply each by its rough cost, and sum; work on the slowest resource first (network, disk, memory, CPU), weighted by how often each is used. Look for a better complexity class before tuning constants.
- **Profile before changing code.** A CPU profile (flame graph) for on-CPU time, an off-CPU or wait profile when latency is high and the CPU idle; for a whole-system slowdown, check each resource's errors, utilisation and saturation first. A kernel being hand-tuned is first classified as front-end, memory, speculation or retiring bound, since each needs a different fix. The profile is kept as evidence.
- **Make the common case cheap:** a fast path checked first, precomputed tables for per-item decisions, loop invariants hoisted, expensive values computed only when used, slow and error paths marked cold and moved out of line.
- **Hot data is compact.** Smaller integer types, hot and cold fields split, structure of arrays where a loop reads one field, arrays or bit sets instead of maps for small dense keys, indices instead of pointers between elements of one array, flat tables instead of a node per element. Fields written often by different threads sit on separate cache lines.
- **Pages cost time.** A buffer the next step overwrites completely is not filled first (each first touch of a page is a fault counted in wall time); large buffers are released as soon as their last reader finishes.
- **Hot paths allocate once.** No allocation or cloning inside loops: reuse buffers sized from what is known, never build an intermediate collection only to iterate it once, and never format a value only compared or written out.
- **No repeated parsing** on a hot path: a value is parsed once and its parsed form passed on.
- **Reuse existing optimised kernels** (the standard library's or a dependency's search, hashing or SIMD routines) rather than writing your own loop.
- **Where the runtime schedules async tasks, blocking work runs on a thread meant for it.**
- **Static dispatch on hot paths;** dynamic dispatch only at boundaries crossed once per request or less.
- **One variant per data shape, chosen once.** A loop that would branch per element on something fixed for the whole input (pixel layout, opacity, a format, a CPU feature) is specialised at compile time and the variant picked once per input or process.
- **SIMD where it measures faster,** with a scalar tail and one helper per repeated vector pattern. A shipped binary targets a baseline CPU; faster variants for newer CPUs are chosen at run time once per process, never by building for the build machine's CPU. Each instruction-set path is kept per target only where its bytes buy measured time on that target.
- **Locks are short:** no I/O, allocation-heavy work or costly destruction inside a critical section; one lock per batch, not per item.
- **Parallelism is bounded and paid for.** Work goes to another thread only when it is larger than the hand-off and cores and memory bandwidth are free; a parallel change reports total CPU beside wall time and is not kept when it buys wall time with more CPU unless the user agrees.
- **No logging, formatting or stats collection inside inner loops;** check whether they are on once outside, and sample costly stats.
- **Compiler and linker settings are claims too:** per-file optimisation levels (hot code for speed, cold code for size), link-time optimisation, profile-guided optimisation (its profile from a representative workload, kept and regenerated when the code it covers changes), dead-section removal and hidden symbol visibility are each kept only with before and after numbers for size and time on every shipped target.
- **Connections:** a database pool's size is set explicitly.
- **Start-up** does not wait on other services: connecting, fetching keys, listing tools and loading what can wait happen on first use or in the background, unless the program can answer nothing without them.
- **Benchmarks** for a claim about production run at the deployed instance's size.
- **What a measurement reports:** wall time, CPU time (user plus system), peak resident memory and, for a shipped binary, its size on every target; hardware counters (instructions, cycles, cache and branch misses) where available, since they move less than time. Commands are compared with a tool that repeats and summarises them (`hyperfine`, `poop`), never one timed run.
- **Microbenchmarks prove they measure the work:** inputs the compiler cannot fold, results consumed through the language's keep-alive (`std.mem.doNotOptimizeAway`, `std::hint::black_box`, `runtime.KeepAlive`), the kernel's disassembly read once; warm-up runs first, then the minimum and the median with their spread, and a wide spread reported as noise.
- **Name the machine's state:** power source, idle or not, frequency scaling, cold or warm caches. A laptop or turbo result is provisional; a claim about production keeps production's settings.
- **Measured figures live in the PR or commit message,** never in code comments, where they go stale; a comment says what the code relies on, and links to the measurement if it must.
- **A measurement PR carries a table:** metric, before, after, absolute difference and percentage, with links to the kept evidence. A cell not measured or not applicable says N/A and why, so no table implies a gain or a lack of regression nobody measured.
- **Name what was compared:** the commits, the hardware, cold or warm runs, and the settings and inputs that change the result. Timing arms are repeated and rotated so noise is not read as a gain; one pass is provisional. A component's figure is labelled as such and never stands for the entry point's.
